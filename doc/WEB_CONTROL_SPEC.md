## Scope and behavior

1. The clock supports **15 annual birthday entries**. Each entry retains the existing enabled state, day and month, local announcement hour and minute, optional birth year, and last handled year. The optional birth year does not change annual recurrence. February 29 occurs only in leap years. Existing birthday audio, priority, quiet-hours behavior, and 30-minute pending expiry remain in effect. All 15 entries must be available through the physical editor, USB commands, persistence, and the browser editor. A change to one entry must not change another entry.
2. The clock has **one countdown timer** with a selectable duration from **00:00:01 through 23:59:59**, inclusive (1 through 86,399 seconds). This range applies to physical editing, USB, browser commands, validation, and status. The existing start, cancel, completion, and audio-priority behavior remains. There are no independent timers for individual browser clients.
3. The web profile supports **four simultaneous browser clients** using the control page, including overlapping status requests and control attempts. This is a runtime concurrency requirement. It is distinct from the existing capacity for **four stored browser authorizations**, which counts home/direct scoped remembered credentials. Four stored authorizations alone do not demonstrate four concurrent clients. The existing command serialization, conflict detection, retry safety, access checks, and home-trust rules continue to apply when clients act at the same time.
4. Music-player actions use ordinary buttons: **Previous, combined Play/Pause, Next** in one row, with **Stop** centered below. The central button is wider and sends Play, Pause or Resume according to live state. This layout supersedes the earlier circular layout as requested on 2026-11-13. No rotation gesture or track seeking is required. Existing playlist behavior remains controlled by the clock.
5. The alarm editor offers a **Test/Stop** button to the right of the music-track number. It auditions the selected folder 08 track without applying or saving the alarm draft, through the alarm output preference with LOCAL fallback. The audition plays one track, closes on completion and can be stopped by the same button or from the player. The button follows the device-reported audition state, including paused playback and changes from other browsers, and returns to Test when audition ends. Existing timer, alarm, mute and physical-editor guards apply. Repeated Test requests use the shared command sequencing and idempotent retry handling.
6. The existing alarm count, settings controls, local HTTP access modes, and audio routing remain in scope for regression checks. This change does not add one-time reminders.

## Existing implementation and required changes

At the start of this expansion, branch `codex/phone-control` had five birthday entries (`CLOCK_BIRTHDAY_COUNT`), a four-hour countdown limit (`CLOCK_TIMER_MAX_SECONDS`), four stored browser authorization slots (`PHONE_BROWSER_MAX`), two in-flight HTTP POST slots, a 2,048-byte status response allocation, and a 16 KiB lwIP heap in the web profile. These were baseline implementation facts, not proof of the new runtime targets. See [birthday.h](../firmware/pico2w_c/app/birthday.h), [countdown.h](../firmware/pico2w_c/app/countdown.h), [phone_settings.h](../firmware/pico2w_c/services/phone_settings.h), [phone_web.c](../firmware/pico2w_c/services/phone_web.c), and [lwipopts.h](../firmware/pico2w_c/services/lwipopts.h).

The baseline Flash v13 record was 512 bytes and filled its two programmed 256-byte pages. The birthday records and optional birth years were embedded in this record. Expanding to 15 entries therefore requires a new versioned storage layout and migration; simply increasing the count cannot fit. Preserve the existing clock A/B sectors, the read-only legacy sector, unrelated sectors, CRC validation, sequence handling, and the rule that loading alone never writes Flash. The migration must read existing v1-v13 settings, retain all five existing birthday entries and other settings, initialize entries 6-15 disabled, and write the new format only on an authorized settings save. Document the resulting rollback boundary before any device installation. See [settings_store.c](../firmware/pico2w_c/services/settings_store.c) and [settings compatibility](NETWORK_TIME.md#settings-compatibility-and-rollback).

The baseline birthday pending mask and claim result were 8-bit values. Widen them for 15 slots, including all uses in runtime scheduling, diagnostics, and tests. Check USB/menu index bounds and the per-entry queued timestamps. The timer range must be updated consistently in the countdown engine, physical timer editor and quick adjustment, USB parsing, browser request validation, and browser duration inputs; reject out-of-range values rather than silently accepting an unintended duration.

The current browser API exposes one shared `/status.json` snapshot and authenticated `/timer`, `/player`, and `/birthday` commands. Expand the birthday array to 15 records while retaining one-record edits, revisions, conflict responses, command IDs, nonces, and idempotent retries. Keep the timer status and command contract consistent with the new duration range. Four concurrent clients require explicit HTTP/lwIP capacity and contention checks; the four persisted credential slots are a separate limit. Do not expose credentials in status. See [phone_access.c](../firmware/pico2w_c/services/phone_access.c), [phone_web.c](../firmware/pico2w_c/services/phone_web.c), and [existing browser behavior](../experiments/phone_control_ap/README.md).

The embedded page must offer all 15 birthday entries, a timer editor covering hours, minutes, and seconds through 23:59:59, and the player transport layout described above. The timer editor uses three Android-style scrolling wheels with the selected row highlighted, supporting touch, mouse scrolling, row selection and keyboard arrows. Digit scale and opacity vary continuously with distance from the selected row to avoid abrupt size changes during scrolling. Button activation must work by mouse, touch, and keyboard. No player rotation gesture or playback position/seek endpoint is specified.

## Acceptance criteria

- Old valid settings load with the five original birthdays unchanged; entries 6-15 start disabled. A successful save and restart retain all 15 entries, optional birth years, handled years, alarms, network settings, audio preferences, browser authorizations, and known Bluetooth devices. A failed or interrupted save retains a valid A/B fallback.
- Birthday validation, annual claim, leap-day handling, pending delivery/expiry, editing, and browser conflict detection work for entries 1, 5, 6, and 15, including simultaneous due entries.
- The single timer accepts 00:00:01 and 23:59:59, rejects zero and values above the maximum at command boundaries, and completes once. Physical, USB, and browser controls report the same duration and running state.
- Four independently opened browser clients can remain active, poll status, and issue overlapping requests without corrupting responses, losing authorization state, duplicating commands, or interrupting audio. Expected contention returns a defined busy/conflict result and permits retry. Test home and direct modes separately; the clock serves one mode at a time.
- The player controls remain usable at a narrow phone width and with keyboard focus. The combined Play/Pause button sends the correct action for playing, paused and closed states. Stop is centered beneath it. Track Test retains the draft and saved alarm settings and stops after one track. There is no rotation or seek interaction.
- Before device installation, host checks cover storage migration and power-loss fallback, maximum status size, HTTP request/response capacity, four-client contention, and memory/build-size headroom. Hardware acceptance follows each separately approved installation.

## Countdown completion versus scheduled alarms

The countdown finish announcement is not a scheduled alarm occurrence. Its separate Stop timer sound button and `overview.timer_sound_id` / `/timer stop_sound` command are implemented and were installed with approval on November 13 as `1.0.0+26.g3717033`; the user subsequently confirmed correct operation. Existing Cancel timer continues to cancel the countdown, while alarm stop/snooze/cancel-repeat retains its scheduled-alarm meaning. Runtime ownership IDs and standard command retries protect later/other audio. Polling accelerates to 250 ms during the last five countdown seconds and completion/ringing; actual end-to-end latency under real radio/decoder load is not yet measured.

## Independent countdown completion options (user acceptance pending)

Before continuing player expansion, the user prioritized timer completion choices. The message is an independent boolean (`timer_voice`), extra sound is Signal=0/Music=1/None=2 (`timer_sound`), and `timer_track` selects 1-255 in folder 08. Defaults preserve message + signal. A checkbox plus mutually exclusive extra-sound choices supports message-only, signal-only, music-only and silent completion. Values are published in `settings` and updated through the existing authenticated `/settings` queue; changing them requires idle audio/stopped timer and closed editors. Physical menu and USB paths share the same apply/validation logic. No audio assets or start/cancel phrase changes are included. Nondefault preferences use conditional Flash v15; see phone-control documentation for compatibility and pending hardware tests.

## Random event music (user acceptance pending)

Timer `settings.timer_random` is a saved boolean applied through `/settings timer_random 0|1`. Each alarm record's sound value adds RANDOM=2; SIGNAL=0 and fixed MUSIC=1 are unchanged. The per-slot revision allocates two sound bits to keep compare-and-apply lossless. Existing command IDs, nonces, scopes and physical-editor/idle guards are retained. The UI keeps the fixed track as a remembered value, disables timer fixed-track editing while random is applied and skips fixed-track audition for random alarm drafts. File catalog, one-choice-per-occurrence behavior, mirror-card requirement, v16 storage and pending hardware checks are specified in [RANDOM_EVENT_MUSIC.md](RANDOM_EVENT_MUSIC.md).

## Optional timer pre-warning (installation pending)

A saved `settings.timer_warning` boolean, default 0, is updated through authenticated `/settings timer_warning 0|1`. The existing checkbox Apply, id/nonce retries, idle guards and snapshots are reused. It is independent of timer_voice, timer_sound, timer_random and timer_track. No browser-generated audio or network-driven second timing is used; the clock owns the monotonic 5..1 schedule. See [TIMER_PREWARNING.md](TIMER_PREWARNING.md) for skip/priority behavior, numeric asset and conditional Flash v17.
